# Architecture

maki-mobile follows the workspace
[Flutter architecture standard](../../../docs/flutter-architecture-standard.md).
This file records how this project applies it.

## Layout

```
lib/
  main.dart                   config → time zones → device token → API client and session → restore → App
  app/
    app.dart                  config, API client, device token and session above MaterialApp.router
    router.dart               routes, the cashier's shell, and redirectFor: the session guard
    routes.dart               the routes' names, apart from the router, so a screen can navigate
    locale.dart               device language if supported, otherwise Indonesian
    theme/tokens.dart         DESIGN.md colours, radii, spacing, breakpoints
    theme/app_theme.dart      ThemeData + MakiTokens (context.tokens)
  core/
    api/                      createApi, ApiInterceptor, apiCall, ApiException, apiErrorMessage
    auth/                     SessionCubit, SessionState and Account (freezed), Permissions, SessionApi,
                              TokenStorage, DeviceTokenStore
    config/app_config.dart    --dart-define values, checked at startup
    utils/                    formatRupiah, formatCount, formatRate, formatDate/DateTime/Time, WindowSize
    widgets/                  FormBanner, used by the auth screens and the cashier's
  features/
    auth/data/                AuthRepository: sign in, change password, reload the account
    auth/presentation/        LoginCubit, ChangePasswordCubit, their screens, the no-access screen,
                              validators
    pos/domain/               the cashier's rules in plain Dart — totals, a voucher's discount,
                              receipt numbers and the outlet's day, order IDs, the cart, checkout,
                              the menu filter, the floor and its tables — and its models (freezed)
    pos/data/                 PosRepository: catalog, device, activation, a voucher's check, the
                              floor, releasing a table, orders, today's orders, void
    pos/presentation/         PosShell (the frame, its Cubits and their bridges), the Cubits, the
                              screens (sell, order, tables, today's orders, one order, account),
                              widgets (the floor among them)
  l10n/                       app_id.arb (template), app_en.arb, generated AppLocalizations
android/app/src/main/         MainActivity.kt, AndroidManifest.xml, res/xml/data_extraction_rules.xml
packages/api_client/          generated by `make api`, never edited by hand
openapi-generator.yaml        generator options (json_serializable, package name)
openapi-templates/            one template override (see docs/README.md)
env/example.json              template for env/<flavor>.json
assets/fonts/                 Plus Jakarta Sans, one static TTF per weight, and its OFL licence
test/helpers/                 fakes (token storages, session API, HTTP adapter), pumpApp (the whole app),
                              the cashier's data (pos.dart) and steps (cashier.dart), pumpUntilFound
integration_test/             the cashier on a device against a real backend
```

The font's licence is bundled as an asset and registered with
`LicenseRegistry` in `main.dart`, so it shows on the app's licence page as
the SIL OFL requires.

Generated types stay in the data layer. `ClientSessionApi` and
`AuthRepository` turn the API's `Me` and `Session` into the app's `Account`
and `IssuedSession` (`core/auth/account.dart`); `PosRepository` turns the
cashier's DTOs into the models of `features/pos/domain`. Only they, and the
code that builds the client and the repositories, import `maki_api_client`.
Features get a `domain/` folder when they have models of their own.

`Account` carries what `GET /me` says about access:

- `permissions`, a set of codes;
- `outlet`, an `AccountOutlet` with the outlet's code, name, time zone and
  language, or null for the Owner.

`account.can(Permissions.checkoutCreate)` asks for a permission by its code
(`core/auth/permissions.dart`), never a role by name. `canUseCashier` is
whether this app is for the user at all.

## State and dependencies

- `SessionCubit` is the only app-wide Bloc ([below](#session)).
- `main.dart` builds every dependency once. `App` provides the config, the
  API client and the device token store with `MultiRepositoryProvider`, and
  the session with `BlocProvider.value`.
- Screen Cubits are created by their screen's `BlocProvider`, with the
  repository built from the provided client: `LoginCubit` and
  `ChangePasswordCubit`, which emit a `SubmitState` (idle, submitting,
  failed with an `ApiException`, or done); `TodayOrdersCubit` and
  `OrderCubit`.
- The cashier's shared Cubits — `CatalogCubit`, `DeviceCubit`, `SaleCubit` —
  belong to its frame, `PosShell`, the `ShellRoute` around every cashier
  route: they live while the cashier is open, so the order being rung up
  stays while the cashier looks at today's orders, and they close when the
  user signs out ([below](#the-cashier)).
- All of them are Cubits. `SaleCubit` drops a second tap on Pay itself: the
  order goes pending before the request is sent.

## Session

- The access token lives in memory only. The refresh token is in
  `flutter_secure_storage`, behind `TokenStorage`
  ([security.md](./security.md)).
- `start(IssuedSession)` keeps a session that sign-in or a refresh
  returned. `updateUser(Account)` replaces the user after a change to their
  account.
- `restore()` runs before the first frame: a stored refresh token gets a new
  access token, so a signed-in user never sees the sign-in screen.
- `refresh()` is shared: calls that overlap wait for one request, because a
  refresh token sent twice would end the session. A refused token clears
  storage and signs out. A network failure keeps the token for the next
  attempt, since nothing says the session has ended.
- `signOut()` tells the server when it can reach it, then forgets the
  session either way. `signOut(reason:)` is the app ending it by itself:
  the state keeps the reason (`SignOutReason.deviceRevoked`), and the
  sign-in screen says why.

## Navigation

`app/router.dart` declares named routes, named in `app/routes.dart`:

| Route | Name | Screen |
| --- | --- | --- |
| `/login` | `Routes.login` | sign-in |
| `/change-password` | `Routes.changePassword` | the password change |
| `/no-access` | `Routes.noAccess` | for a user the app isn't for |
| `/pos` | `Routes.pos` | selling |
| `/pos/order` | `Routes.posOrder` | Detail Items full screen, below 840dp |
| `/pos/tables` | `Routes.posTables` | the outlet's tables, when it has some |
| `/pos/history` | `Routes.posHistory` | today's orders |
| `/pos/history/:orid` | `Routes.posOrderDetail` | one order: its receipt and void |
| `/pos/account` | `Routes.posAccount` | who is signed in, this device, sign-out |

The `/pos…` routes share one `ShellRoute`, whose builder is `PosShell`. The
navigation's places (`/pos`, `/pos/tables` when the outlet has tables,
`/pos/history`, `/pos/account`) are `NoTransitionPage`s, as tabs; the order
and an order slide in over them.

`redirectFor`, a pure function tested on its own, runs again on every
session change through `refreshListenable`. The first row that fits
decides:

| Session | Goes to |
| --- | --- |
| Signed out | `/login`, from anywhere |
| Signed in without `checkout.create` — the Owner, or staff whose role doesn't allow checking out | `/no-access`, from anywhere. First, because the app isn't theirs: not even a password of their own is needed to be told so |
| Signed in, must change their password | `/change-password`, from anywhere; its app bar has sign-out, so the device can go to someone else |
| Signed in | Away from `/login` and `/no-access` to `/pos`; `/change-password` stays reachable by choice |

The no-access screen names the account signed in and what to do:

- **The Owner** is told the app is for cashiers and the Owner works in the
  web admin.
- **Staff** are told their role at their outlet doesn't allow checking out
  yet. **Check again** refreshes the session, which brings the permissions
  back as they are now. If checking out is among them, the redirect opens
  the cashier, or the password change if one is due.
- **Sign out** frees the device.

The backend checks every request regardless: the router only keeps screens
that would be refused out of reach.

## API client

`createApi` builds one Dio with the configured base URL, the session, and
`ApiInterceptor`. It hands the Dio to the generated `MakiApiClient` with an
empty interceptor list, so the generator's own auth interceptors never run.

- Every request carries `Authorization: Bearer …` when signed in,
  `X-Device-Token` once the phone is one of its outlet's cashier devices
  (as the browser's device cookie covers all of `/api/v1`), and
  `Accept-Language` in the user's language, or the device's before sign-in.
- A `device_revoked` answer, to any request, wipes the device token and
  ends the session (`signOut(reason: deviceRevoked)`): a revoked phone keeps
  nothing that let it in ([security.md](./security.md#cashier-device)).
  Requests that learn it at the same moment share one sign-out.
- A 401 from anything but the auth endpoints triggers `session.refresh()`,
  and the request is retried once through the same Dio. If the refresh
  fails, the session has ended and the user is back at sign-in.
- `apiCall(...)` awaits a generated call and turns its failure into an
  `ApiException`. That's the envelope's `code`, `details` and request ID,
  `internal_error` for a response without an envelope, or `network` when no
  response came.
- Screens show `apiErrorMessage(l10n, error)`: the translation of the code,
  with its details filled in (`rate_limited` says how many minutes), or the
  server's message for a code without a translation.

## The cashier

The cashier is `features/pos`, in DESIGN.md's layouts: below 840dp a bottom
navigation (Kasir, Meja when the outlet has tables, Riwayat, Akun) with the
cart bar above it, from 840dp a navigation rail beside the menus and the
Detail Items panel ([design-system.md](./design-system.md)).

**The frame** (`PosShell`) builds the `PosRepository` for the user's outlet
and the four Cubits its screens share. Cubits don't call each other
(standard §4), so the frame bridges them with `BlocListener`s:

- the catalog loads → the order follows it (`SaleCubit.follow`);
- a sale is taken → the device's count moves past its number at once
  (`DeviceCubit.sold`), the catalog loads again for the stock it took, and
  the floor for the customers it seated;
- a sale is refused → what the refusal names loads again: the device for a
  `device_*` code, the floor for `table_unavailable`, the catalog and the
  floor for `dine_in_mode_changed`, the catalog for the rest;
- the app comes back to the front → they all load again; in the
  background the catalog and the floor stop loading every 30 seconds.

A snackbar stays on the place it was shown on: moving to another of the
navigation's places, or opening the order full screen, takes it away
(`_FrameState.didUpdateWidget`), since it shows where the order's pay
button is. *Meja A1 dikosongkan.* says its word on the tables' page, and
then is out of the way at the till.

**The device** (`DeviceCubit`) asks `GET /pos/device` when the cashier
opens, after each sale, and when the app comes back to the front. A phone
the outlet hasn't activated gets `DeviceGate`: its Manager, signed in on
it, names it and activates it there (`POST /outlets/{oid}/devices` with
`platform: android`); `PosRepository.activate` keeps the token the answer
carries in `DeviceTokenStore`, and the next request carries it. Anyone else
is told to ask a Manager. A revoked phone never stays on this screen: the
API client signs it out ([above](#api-client)).

**The catalog** (`CatalogCubit`) loads in one request, again every 30
seconds while the app is in front, after each sale and void, and on
resume; loads that overlap share one request, and a failed reload keeps the
catalog in hand. The server decides every sale against the stock as it is.
It says how the outlet seats its dine-in customers too (`dineInMode`): at
its tables, or by the number stands the cashier hands out.

**The tables** (`FloorCubit`, `GET /pos/tables`) are the outlet's areas
that hold tables, in order, with each table's status; whether there are
any decides the navigation's Meja. Where the outlet seats its customers by
number stands there are none, and the tables screen, as the catalog says,
tells why instead of showing a floor. The floor loads again when the tables
screen or the picker opens, after a sale or a release, every 30 seconds
while the app is in front, and on resume; a failed reload keeps the floor
in hand.

- The tables screen (`TablesScreen`) shows it an area at a time
  (`FloorPanel`): a chip per area, the key, the layout and the tables not
  placed on it. A table opens a sheet with its status and, while customers
  are seated there, since when and how many sales; *Pesan di meja ini*
  while it can be picked (available or occupied), which makes the order
  dine-in at that table and opens the sell screen; and *Kosongkan Meja*
  once its customers have left, after asking (`FloorCubit.release`,
  `POST /tables/{tid}/release`).
- In Detail Items, a dine-in order has *Pilih meja* when the outlet has
  tables, always optional (`TableChoice`). It opens the floor full screen
  on a phone and as a dialog on a tablet (`pickTable`), where only an
  available or occupied table can be picked, on the area of the table
  picked before. The table picked shows with *Ganti* and the button that
  lets it go; a takeaway lets go of it.

**Number stands.** Where the catalog says `number`, a dine-in order has the
*Nomor papan* field in Detail Items instead of *Pilih meja* (`StandField`):
the number as the stand shows it, by `stand.dart`'s rule, the server's —
1–10 letters, digits and hyphens, a hyphen only between them — shown in
capitals as it is typed, and sent trimmed. Pay stays off until it is one the
server takes; what it takes is said once the cashier leaves the field. A
takeaway and the next customer let go of it. When the catalog loads with the
other way, `follow` takes off a table picked where the outlet now takes
number stands, or a number typed where it now seats at tables, and a notice
says so.

**The order** (`SaleCubit`) holds the type, the lines (menu, qty, note —
never a price), the voucher, the table or the stand's number, the order
pending, the notices and the last sale. The rules are `features/pos/domain`, in plain Dart:

- `totals.dart`: the server's rule in integers, tested against
  `../maki-be/api/test-vectors/order-totals.json`, the file the backend and
  the web read too;
- `voucher.dart`: a voucher's terms and its discount (`voucherDiscount`),
  tested against `../maki-be/api/test-vectors/voucher-discounts.json` the
  same way;
- `cart.dart`: a line takes at most the stock there is (999 untracked),
  100 lines, a note of 100 code points; `reconcile` takes out what the
  catalog no longer sells or has none of, and cuts what it has too little
  of — which `follow` says in a notice;
- `receipt_number.dart`: the outlet's day of an instant in its time zone,
  and `OUTLET-DEVICE-YYYYMMDD-0001`;
- `order_id.dart`: a CUID2-shaped ID from `Random.secure`;
- `stand.dart`: a stand's number as the server keeps it, and whether it
  takes it (`validStand`);
- `checkout.dart`: the cart at the catalog's prices with the voucher's
  discount off, and whether the voucher applies (`priced`), the order made
  once with its voucher's code and its table or its stand's number
  (`makeOrder`), renumbered
  (`renumber`), and the device's count after a sale (`afterSale`);
- `floor.dart`: the floor and its tables, which of them the cashier can
  sell at (`selectable`), and finding one by its ID.

**The voucher** the customer gives is typed in Detail Items and checked
with `POST /vouchers/validate` (`SaleCubit.applyVoucher`), from the phone as
the outlet's till. Its terms stay with the order, one per order, and its
discount is worked out again as the cart changes. Short of its minimum
spend, Detail Items says so and Pay is off; a refused code says why under
the field. It can't change while a sale is pending, and goes with the
sale.

**Charging** never charges twice:

- an order is built once, with its own ID and the device's next receipt
  number of the outlet's day, and goes pending before it is sent;
- no answer, or a 5xx: it is sent again exactly as it was, by itself after
  1 and 3 seconds, then from Kirim ulang; the cart can't change meanwhile,
  and the cashier may let it go with a warning to check today's orders;
- `order_no_taken`: renumbered from `GET /pos/device` under the same ID, at
  most twice;
- a voucher's refusal (used up, expired, turned off, another outlet's,
  short of its minimum) takes the voucher off the order and says why;
- `table_unavailable` (the table was turned off, scheduled off or deleted
  since it was picked) takes the table off the order and says why, from
  the refusal's `details.status`, while the frame loads the floor again;
- `dine_in_mode_changed` (the Manager changed how the outlet seats its
  customers since the catalog loaded) takes off the table, or the stand's
  number, the way the refusal's `details.mode` names has no place for, and
  says so, while the frame loads the catalog and the floor again;
- any other refusal frees the cart and says what changed — prices, the
  rates, the method, the stock, or the phone's clock when the server
  refuses `client_created_at` — while the frame loads what it names.
  `total_changed` with a voucher checks its terms again too, and takes it
  off if the sale can't take it any more.

The payment is one dialog (`openCheckout`): the cash received, grouped as
it is typed, the quick amounts (exact, 50.000, 100.000, off below the
total) and the change; then, without an answer, Kirim ulang and Batalkan;
then the receipt, and Transaksi baru for the next customer.

**Receipts** (`ReceiptView`) are in the outlet's language and number style,
whatever the screen's (`lookupAppLocalizations(Locale(outlet.locale))`), as
the spec prints them and the web shows them; times in the outlet's zone. A
voucher's discount is *Potongan (KODE)*, a dine-in order's table is under
its type, and a stand's number shows large under the outlet's name, for the
waiter who brings the order. The receipt shows on screen after the sale and on an order's page; printing,
to a Bluetooth printer, comes later.

**Today's orders** (`TodayOrdersCubit`) load a page of 20 at a time,
searchable by part of a receipt number, each with its table or its
stand's number ("No. 12"). More is counted by pages, not by
the orders shown: an order made meanwhile is on the first page, which a
pull to refresh brings. An order's page (`OrderCubit`) has its receipt and,
with `order.void`, the void, for a reason; one voided by someone else
meanwhile loads again as it is.

**The account** (`AccountScreen`): the user, the outlet, this device and
today's date at the outlet, which DESIGN.md's phone layout moves off the
sell screen. Signing out asks first while an order is being rung up; the
device token stays for the next cashier.

## Flavors and configuration

| Flavor | Application ID | App name | HTTP |
| --- | --- | --- | --- |
| `dev` | `com.kervzent.maki_mobile.dev` | Maki Dev | HTTPS, plus plain HTTP to `10.0.2.2` and `localhost` |
| `prod` | `com.kervzent.maki_mobile` | Maki | HTTPS only |

Configuration comes from `--dart-define-from-file=env/<flavor>.json`:
`APP_ENV`, `API_BASE_URL` (required) and `SENTRY_DSN` (empty turns error
reporting off). `AppConfig` stops the app at startup naming every missing
value. These values are compiled into the app — never put a secret there.

## Android

- `MainActivity` turns off Android's default focus highlight on the Flutter
  view. A key from a hardware keyboard or a barcode scanner takes Android
  out of touch mode, and it would then outline the whole screen. Flutter
  draws its own focus indicators.
- The manifest declares `INTERNET` itself, turns backups off, and allows
  cleartext only in the `dev` flavor's network security config
  ([security.md](./security.md)).

## Text, money and time

- Every user-facing string comes from `AppLocalizations`; the ARB files live
  in `lib/l10n/`, and a test fails when a key is missing in one of them.
- Before sign-in the app speaks the device's language, if supported, and
  otherwise Indonesian. Signed in, it speaks the language set on the user's
  account, the same on every device.
- `formatRupiah` gives `Rp 25.000` / `Rp 25,000`, the same as the web app;
  `formatCount` groups counts, `formatRate` writes basis points as `5,5%`.
- `formatDate`, `formatDateTime` and `formatTime` always take the outlet's
  time zone — never the device's, which may be set to anything; the full
  time zone database is bundled, so it works offline. The account screen
  and the wide sell screen's header show today's date there. The router
  takes the clock as `now` and hands it to the screens and the orders, so a
  test can fix it.
- A receipt speaks the outlet's language whatever the screen's
  ([above](#the-cashier)).
- `WindowSize` (compact < 600dp, medium, expanded ≥ 840dp) decides layouts,
  following DESIGN.md's breakpoints.

The fakes in `test/helpers/fakes.dart` build a cashier (`testUser`,
`testAccount`, with `permissions` and `outlet` to vary), a Manager
(`testManager`), the Owner (`testOwnerMe`), and an outlet (`testOutlet`,
with its time zone); `test/helpers/pos.dart` builds the cashier's models
and the API's JSON for them.

Widget tests never wait a fixed time. They `pumpUntilFound` the outcome,
or `pumpUntil` a condition, which move the fake clock as they go: Dio
starts every request with a zero-length timer, which a bare `pump()` never
fires. Their font's glyphs are as wide as the font is high, so a row that
fits on a phone can overflow in a test first: rows of a label and its value
(`LabelValue`) give the value at most 60% of the line and let it wrap.

**On a device** (`integration_test/cashier_test.dart`): the outlet, its
Manager, its cashier and its menu are set up through the API, as the web's
cashier e2e does; then the Manager activates the phone, sells with change,
finds the sale and voids it, the cashier sells on the same phone, then
with a voucher the Owner made for the outlet (its discount on the receipt,
and its use taken, as the Owner sees it), then at a table picked from the
floor, which the receipt names and the tables screen shows occupied until
the cashier releases it, and once the Manager revokes it
the phone signs out with the notice and holds no token. It needs the
backend's Owner:

```
flutter test integration_test --flavor dev --dart-define-from-file=env/dev.json \
  --dart-define=E2E_OWNER_USERNAME=... --dart-define=E2E_OWNER_PASSWORD=...
```

Without them it skips. Each run makes its own outlet and accounts.
